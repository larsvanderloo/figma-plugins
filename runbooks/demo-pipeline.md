# Demo pipeline — in-between-review demos

Owned by `release-engineer`. Distinct from formal validation (`ui-engineer`'s e2e gauntlet) and formal usability tests (`release-engineer`'s panels).

This is the everyday flow for "look at my change before I ship it." Fast, deterministic, reproducible — but not a substitute for validation. Full role description in `.claude/agents/release-engineer.md`; this document is the operational playbook.

---

## 1. What a demo is

A demo is a captured run of the plugin against a canonical source file with a parameter manifest, producing screenshots, a video recording, a small gif, console output, and a sidecar manifest with full provenance. Demos are reviewable side-by-side against prior tag's demos via a static review site.

A demo is **not**:

- A test (no pass/fail; visual signal only).
- A formal validation (use the e2e gauntlet for that).
- A usability test (use `release-engineer`'s protocols).
- A replacement for hands-on review (it complements it).

## 2. Source library

`tools/demos/sources/` holds canonical Figma documents per editor type. See `.claude/agents/release-engineer.md` §"Source library structure" for the layout.

Adding a source:

1. Open a PR adding the `.fig` file (LFS-tracked) and its `.json` metadata sidecar.
2. `release-engineer` reviews license: internally-created files require a `source: internally-created` field; third-party files require a verified license link.
3. Update `tools/demos/sources/manifest.json` with the new entry.
4. PR merged — the demo tool picks up the new source automatically.

Removing a source: deprecate, never delete. Mark `deprecated: true` in the metadata; the demo tool skips it but past-demos against it remain reproducible.

## 3. Parameter manifests

`tools/demos/manifests/<plugin>/` holds per-plugin parameter sets. See `.claude/agents/release-engineer.md` §"Parameter manifests" for the schema.

Standard sets per plugin family in `tools/demos/parameter-set-conventions.md`. Plugin-specific sets are added with a description and an ADR justifying them.

## 4. The demo tool

The headless demo tool (`tools/demos/demo-tool/`) is deferred to a future sprint. The MVP for now is **manual demos**:

1. Engineer builds the plugin (`pnpm --filter @figma-plugins/<slug> build`).
2. Engineer opens Figma desktop, imports the manifest, walks through the flow on a canonical source file, captures screen recording with QuickTime + screenshots with `Cmd-Shift-4`.
3. Output named per the convention (`<plugin>-v<version>-<commit-short>-<source-id>-<param-set>.<artifact>`).
4. Sidecar manifest hand-written for now (or generated by a small script).
5. Uploaded to S3 via the demo CLI (also deferred — for now, attach to the PR description).

When the demo tool lands, it automates steps 2–5 deterministically.

## 5. CI integration

`.github/workflows/demo.yml` is deferred to v0.2. Initial release ships with manual demos.

When wired:

- Triggers on PRs touching `plugins/*/code/`, `plugins/*/ui/`, `components/`, or `sections/`.
- Builds the plugin in production configuration.
- Runs `demo-tool` against the standard parameter sets for representative source files.
- Uploads demos to S3.
- Generates the static review-site bundle.
- Comments on the PR with the review-site link, demo count, and any auto-detected anomalies.

Target: end-to-end under 5 minutes.

## 6. Review interface

Static site at `https://demos.<company>.dev/<plugin>/<pr>/<commit>` (deferred). Manual review for now: PR description with embedded gifs and links to the recordings.

Inline gif previews keep the PR scannable. Full recordings are available for deeper review.

## 7. Auto-checks

When the tool is wired, every demo run captures and gates on:

- **Console errors / unhandled rejections** — any error in the dev console fails the demo.
- **Network failures** — any `fetch` that errors fails the demo (unless the demo's parameter set explicitly tests the offline path).
- **Long renders** — any render frame > 5 seconds flags a warning.
- **Bundle-size delta** — over budget fails; just-under flags a warning.

Auto-checks gate the PR — failing demos block merge until either fixed or explicitly waived (with reason in the PR).

## 8. Storage and retention

S3 layout:

```
s3://<bucket>/demos/
├── <plugin>/
│   ├── pr/<pr-number>/<commit-short>/  # 90-day retention
│   ├── tag/<version>/                  # indefinite retention
│   └── adhoc/<user>/<date>/            # 30-day retention
```

Lifecycle policies enforced by the bucket. Indexed in Monday's `Demo Set` column on the corresponding plugin board.

For the MVP (no S3 yet), demos live as PR attachments. When S3 is wired, an ADR documents the migration path for prior PR attachments.

## 9. Escalation paths

- **Demo reveals a regression** → escalate to `ui-engineer` for the full e2e gauntlet.
- **Demo reveals a perf pathology** → escalate to `figma-api-engineer`.
- **Demo can't reproduce in fresh CI** → that's a demo-tool bug; `release-engineer` fixes immediately.
- **Reviewer disagrees with what the demo shows** → engineer iterates, posts a new demo. Demos are cheap; arguing isn't.

## 10. What demos don't replace

Demos are necessary for fast review but not sufficient for shipping decisions. Always required before a tag:

- E2E gauntlet (`runbooks/e2e-gauntlet.md`) — manual run-through in design + FigJam + slides.
- Validation suite (vue-tsc, vitest, axe, bundle size).
- `ui-engineer` `validation: pass` comment.

A clean demo doesn't replace any of those. A failed demo is a strong signal that validation will fail too — but a passing demo is not a green light.
