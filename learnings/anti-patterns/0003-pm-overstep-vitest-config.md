## Part A: cross-domain action (PR #63)

### What project-pm did

`project-pm` authored and pushed code under:

- `plugins/welder-editor/vitest.config.ts` — owned by `figma-api-engineer`
- `plugins/welder-editor/tests/__stubs__/vue-router.ts` — owned jointly by `figma-api-engineer` (vitest config wiring) and `ui-engineer` (test setup fixtures)

The PR body explicitly flagged the overstep and called for `figma-api-engineer` to review before merge. project-pm did not merge.

### Why it crossed the boundary

Small fix, sprint blocked, mechanical root cause. project-pm scaffolded the branch rather than halting and dispatching — reasoning that a scaffolded branch with a review gate is lower risk than a prolonged broken main. The reasoning is partially valid: the outcome was acceptable and no rollback was required. But it is still a boundary violation.

### What the correct protocol was

Write a clear diagnosis → dispatch `figma-api-engineer` → if unavailable, escalate to human owner for cross-domain authorization. Do not write the code.

### Why it was tolerated

- Fix was mechanically correct (verified by figma-api-engineer)
- PR was not merged until figma-api-engineer reviewed
- Sprint 5 main was blocked; urgency was real
- Files touched (vitest.config.ts, a test stub) are low-risk

## Part B: patching symptoms before auditing root cause

### What happened

The PM-scaffolded hotfix (PR #63) fixed 30 of 37 failing tests (the `UFormField`/`UInput` rendering failures). figma-api-engineer validated and merged it as correct within its stated scope.

However: a subsequent v0.2.1 audit revealed that PR #63 was treating a symptom. The root cause was the missing type foundation — `components.d.ts` and `auto-imports.d.ts` are auto-generated by `@nuxt/ui/vite` during `vite build`, and CI ran `pnpm typecheck` BEFORE `pnpm build`. vue-tsc never saw those declarations, so every `<UInput>` / `<UFormField>` was an "unknown global".

The full fix (PR #65) required:

1. CI step reorder: install → build → typecheck → test → lint
2. `vue-router@^4.5.1` devDep at repo root
3. `shims-vue.d.ts` for the plugin
4. `components.d.ts` / `auto-imports.d.ts` in every section and plugin tsconfig include
5. Two SFC prop-type fixes exposed by the now-working typecheck

PR #63 (the narrow vitest stub fix) remains valid as a defensive layer — the vue-router alias stub prevents regressions if the root devDep is accidentally removed. But it was not the right first response.

### What the correct protocol was

When Sprint 5 Wave 3 PRs started failing CI, the right sequence was:

1. **Audit before patching.** The v0.2.1 reference exists. Before writing any stub or alias, compare the failing project's setup against v0.2.1 file-by-file. This would have surfaced the `components.d.ts` / CI ordering gap in 30 minutes.
2. **Fix the CI ordering first.** The keystone fix (build before typecheck) is a 3-line change in `validate.yml`. Everything else follows from it.
3. **Then assess what stubs remain necessary.** With real `vue-router` installed and the d.ts files generated, the stub is defence-in-depth rather than the load-bearing fix.

### Why this matters

Patching symptoms compounds debt. Each stub or alias added to work around a missing foundation adds a cognitive load for the next agent and creates false confidence that the problem is solved. When the real root cause surfaces later, the workarounds have to be untangled.

The audit cost (30 min to read v0.2.1 file-by-file) was lower than the cost of the cascade of hotfix PRs and the team confusion about why tests kept failing.

## Recommendations

1. **Fast-path agent dispatch instead of hand-rolling** (from Part A): when project-pm diagnoses a broken-main config issue in an owned file, write a 2-3 sentence diagnosis and dispatch the owning agent. Do not write the code.

2. **Audit the reference implementation before patching** (from Part B): when a new library integration breaks CI, compare the failing project against the working reference file-by-file before writing stubs. Cost of audit ≈ 30 min. Cost of compound patching ≈ 3+ PRs and continued CI failures.

3. **CI ordering is the keystone for build-time code-generation tools.** Whenever a tool generates d.ts files during build (Nuxt UI, `unplugin-auto-import`, code-gen pipelines), CI must run build before typecheck. This is not obvious from the error messages (which say "unknown global" or "cannot find module", not "you need to build first"). Document it.

4. **If the team decides to formalize "PM may scaffold a hotfix with explicit review gate":** that exception needs to live in CLAUDE.md as a named protocol, not as a case-by-case judgment call.
